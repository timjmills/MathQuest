# Lesson library — architecture and scale-up plan (2026-09-26)

Owner goal: use the three passing sample lessons (`design/lesson-samples/`, critic lessons-r4: 48/48 pages ≥ 8) as the
model, and build **intervention lessons in the same format** for every WRM small step, every skill, every CCSS standard,
lettered part and EE, housed in a **lesson library**, each tagged WRM / CCSS / EE, each **tied to a skill that practises it
the same way** (by default or through an option), with a **record** of what is covered, what lessons / skills / options
are still needed, and when each standard is fully hit by lessons and by skills. **Nothing is committed below 8/10 from an
independent critic.**

Read with: `design/LESSONS_VISION.md`, `design/LESSON_RULES.md` (every past lesson failure as a rule),
`design/audit/runs/lessons-r1..r4/SUMMARY.md`, `design/audit/LESSONS_LEARNED.md`.

## 1. Units and identity

A **routine** is the teaching: step names, icons, chant, concept, vocabulary pictures, cases (hand-authored, ≈ 240). A
**lesson** is thin: a routine + a practice link (skill + option values) + tags, mostly derived.

| Kind | Id | What | Est. |
|---|---|---|---|
| `wrm` | step id `Y3.B2.S6` | exactly one entry per WRM small step | 872 entries → ≈ 600–650 rendered + ≈ 230 aliases |
| `sup` | `sup:Y2.B4.1` | Awsaj supplements | 36 |
| `ccss` | `ccss:6.NS.A.1` | a CCSS code / part no WRM or supplement lesson teaches (mostly grade 6) | ≈ 23 |
| `ee` | `ee:M.EE.6.SP.1` | EE access lesson not reached by any other lesson | ≈ 30–35 |
| `skill` | `skill:addition:add_missing_digit` | a teachable skill no lesson above practises (and not a variant) | ≈ 60 |

≈ **750 rendered lessons on ≈ 240 routines over 13 archetypes.** Duplicates are avoided three ways: `same` aliases
(identical skill, options and routine), a shared routine across ranges, and `variants` (sibling skills practised under one
routine). One lesson carries many tags: `ccss` / `ee` = union of its steps' v3 codes; parent codes with lettered parts must
be resolved to `parts` (19 parent codes on ≈ 150 steps).

## 2. Files and ownership

| File | Owner |
|---|---|
| `js/modules/lessons/library.js`, `schema.js`, `prereqs.js` (back-compat re-export) | engine lane E |
| `js/modules/lessons/families/{early,placevalue,addsub,multdiv,fractions,measure,timemoney,geometry,data,algebra}.js` — `ROUTINES`, `LESSONS`, `NEEDS` | one lesson lane each |
| `js/modules/lessons/seed-db.js` (GENERATED by `ws-lesson-seed.cjs`), `status-db.js` (GENERATED by `ws-lesson-coverage --write-db`) | never hand-edited |
| `js/modules/sheet/lesson-arch/*.js` — archetype plug-ins | E |
| `js/modules/teacher-lessons.js` — the Lesson library screen | UI lane |
| `design/lessons/{link-report.json,render-stamps.json,milestones.jsonl}` | generated by gates |

Lesson lanes never edit generators, providers, options or the engine: they write `NEEDS`, which `build-list.js` merges
(a need matching an existing entry adds to its `lessonsBlocked`; otherwise a `source: 'lesson'` entry). Shared
registries are append-only. Lessons are referenced by string id only, never by position.

Derived automatically: title, grade, block, CCSS / EE, vocabulary + glossary + stem (`wrm-vocab.json`), WRM key model,
archetype, candidate practice skill (`SKILL_WRM`), default prerequisites and mixWith, I Can, worked-step words (provider),
chart drawings (template `stepState`), needs. Hand-authored per routine: step names, icons, chant, concept, vocabulary
pictures, cases, guided cases, floors. Per lesson: practice option values, resolved parts, prerequisite reasons.

## 3. "Tied to a skill that practises it similarly" — link checks in `ws-lesson-check`

- **LINK-1** every Guided / Independent / Practice / Mixed-lead item comes from `practice.skill` with `practice.opts`.
- **LINK-2** every chart example comes from the same skill and options.
- **LINK-3** the chart's representation (`routine.rep`) is what the practice items draw (≥ 90 %, 100 % when an option fixes
  it), reached by the skill's default or a declared option value.
- **LINK-4** each declared case is dealt; every case the practice deals ≥ 5 % is modelled on the chart.
- **LINK-5** the WRM key model's archetype agrees with the routine's, or the lesson says why (`repWhy`).

A failure records a need: skill not live → `skill`; representation or case not produced but drawable → `option`; provider
steps ≠ routine steps → `steps`.

## 4. The coverage record — `ws-lesson-coverage.cjs` → `design/LESSON_COVERAGE.md`

Node-only (no browser). Modes: default (structure + coverage), `--report-only`, `--report`, `--write-db`, `--json`,
`--family`. Status comes **only** from critic grades files (`design/audit/runs/lessons-*/grades.jsonl`, with `lesson`,
`routine`, `archetype`, `seed`, `basis`, `renderHash`, `tree`, `batch`); a render that changes after a pass becomes `stale`.

Sections: summary by year and grade; CCSS table (code / part, skills verdict, lessons tagged / passed, lesson verdict);
EE table; skills → lessons; **lessons to make**; **skills to make / options to make** (merged with BUILD_LIST, with a
"blocks N lessons" count); archetypes; critic ledger; **milestones** — the date each year, CCSS domain, grade and EE set
first became FULL by lessons and by skills (append-only `milestones.jsonl`).

Verdicts: a WRM step is lesson-covered when its entry (or alias target) has passed; a CCSS code / part is lesson-FULL when
its skills verdict is full and every evidence skill is practised by a passed lesson tagged to it; EEs the same with
`EE_AUDIT`; every live teachable skill must be the practice skill or a variant of a passed lesson.

## 5. Lesson library screen (v1)

`teacher-lessons.js` as a `'lessons'` screen in `teacher-shell.js`, reusing the Skills library two-pane shell. Search
(title, step id, CCSS / EE code, skill), Grade and WRM Year → Block filters, Approved / All drafts. Detail: tags, practice
link (opens the skill), prerequisites, steps with icons, chant, "Preview chart", **Print packet**
(`openPrintWith([{…, role: 'lesson', lessonId}])`), add the practice skill to the set. Gate `ws-teacher-lessons.cjs`;
critic grades screenshots at 1280 / 820 / 390.

## 7. Phases

- **Phase 0 — foundation (engine lane E).** Land `LESSON_RULES.md`, `ws-lesson-check`, `cases`. Render-hash baseline of
  the 3 samples. Build `library.js` / `schema.js` / empty family files; migrate the samples to step lessons;
  `buildLesson(lessonId)` and `lessonId` through `teacher-print`, **samples byte-identical**. Split archetype code out of
  `lesson.js` into `lesson-arch/{fact,column,line}.js` (byte-identical). `ws-lesson-seed` → `seed-db.js`;
  `ws-lesson-coverage` (report-only, r4 samples read as passed); build-list integration; `tests/lib/browser-lock.cjs`.
- **Phase 1 — archetype certification.** Per archetype: 3 pilot lessons spanning its variation; E builds the module,
  `stepState`, icons, vocabulary pictures; the critic grades every page at L and M, seeds 4242 and 1001, keys included,
  until all ≥ 8. Waves: 1a A1, A2, A3, A4, A6 · 1b A5, A7, A10, A8 · 1c A9, A12, A11, A13.
- **Phase 2 — scale certified archetypes per family**, in block order, ready lessons first (skill live, kit-migrated, LINK-3
  passes), R / Y1–Y4 before Y5–Y6. Blocked lessons are recorded, not faked.
- **Phase 3 — non-WRM lessons:** supplements, grade-6 `ccss:`, `ee:` access (age-appropriate pictures), `skill:`.
- **Phase 4 (continuous) — blocked lessons** land as their build-list skills / options pass; skill lanes pick build-list
  entries by "lessons blocked".

## 8. The 8/10 rule at scale

Owner ruling: everything is committed only after an independent critic scores it ≥ 8. At scale:
- Every lesson's four pupil pages (chart, lesson sheet, practice, mixed) are graded **directly** by the critic at the
  default print size (M), seed 4242.
- Keys are checked by machine on every lesson (pixel facsimile + every answer recomputed) and spot-checked by the critic.
- Size L and a second seed are graded directly on every certification lesson and on 2–3 sampled lessons per batch; a
  failure traced to the engine or archetype re-queues that archetype's lessons and tightens the next two batches to full
  grading.
- The grades ledger records the basis (`direct` / `sampled` / `machine`) so what was graded is auditable.
- `ws-lesson-check` (25 seeds, every LESSON_RULES rule, LINK-1…5) must pass before a batch reaches a critic.

## 9. Risks

Engine regressions invalidating passed lessons (single engine owner, render-hash stamps → `stale`); ≈ 359 steps blocked
until their skill / option passes (build list re-ordered by lessons blocked); WRM representation vs our skill (one `model`
option per family, `repWhy`); critic throughput (second critic slot when three or more archetypes scale); `stepState` on 8
more templates (additive exports, skill render gates on every change); data drift (unknown ids fail, lesson ids never
deleted); copyright (WRM titles, vocabulary and stems only; models described in our own words); EE lessons for older
pupils need age-appropriate contexts; the skill-keyed Print "Lesson" role keeps working via `defaultLessonForSkill`.
