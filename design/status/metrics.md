Owner: Wave 0 lane B, step S8 (`design/IMPROVEMENT_PLAN.md` §1.4 S8, §1.6.7, §4.4 "How we will know").

list with a note, so they are written down once.

`git rev-list --count HEAD` → 73 at `d5734a0`, and it grows with every commit). History numbers come from a full clone:

branches, fetched 2026-10-23). Below, `<full clone>` means that directory. The tree holds **722 skill codes**

**Why a new class, DATA_SHAPE (decision 2026-10-23, critic D2).** The critic found duplicate proposals in the MAP and
tagging reports classed REPEAT. REPEAT is a page fault (the same problem twice on a page or packet), so its row now
says so. No existing class fits the rest: UNTRUE_TEXT is a written claim the code does not bear out, and a duplicated
proposal is not a false sentence; TAG_LINK is a wrong pre / related link, and a duplicate build-list entry is not a
link. So DATA_SHAPE (machine, no gate) holds duplicated or overlapping proposals, a proposal for what an existing value
already deals, duplicated rows or clauses and option ids that should fold into one. Where a finding was a padded or
duplicated pre / related link it went to TAG_LINK, and a wrong tag to UNTRUE_TEXT. Two definitions were widened rather
than adding classes: PLAIN_WORDS now names typos, and VIEWPORT already named a sticky header over the answer.
The scan for the three patterns over all 7,878 rows: duplicate proposals 21 rows to DATA_SHAPE, 2 to TAG_LINK, 1 to
UNTRUE_TEXT (of these 24, 16 had been REPEAT, 4 OTHER, 3 UNTRUE_TEXT and 1 TAG_LINK; REPEAT 222 → 206); typos 2 rows to PLAIN_WORDS; pinned / sticky over an answer 1 row to VIEWPORT (the
other sticky-bar rows were VIEWPORT already, or a toast over a control: INTERACTION, which also corrected one
CLIP_OVERLAP row). Print "Model" tab overlaps stay CLIP_OVERLAP: they are a printed label, not a pinned screen element.

### 7.3 Rules

1. **A rising measurable class becomes the next machine check.** After each round, compare each machine class's
   count with its count in earlier Wave 0 rounds. A class that rises (or appears in two lanes) gets a check in S2,
   proved by a **backtest**: it FAILS on the state the critic failed and PASSES on the fix (§1.4 S2).
2. **Appending critic findings to the tally.** Add a new group file pair in `design/status/tally-src/`
   (`findings-G8.csv`, `reports-G8.csv`, then G9 …) with the same columns as the existing ones
   (findings: `report,run,round,defect_id,class,kind,carried,severity,rule_ids,family,template,summary`;
   reports: `report,run,lane,round,date_added,commit_added,verdict,min_score,mean_score,n_open,notes`). Use only
   classes from `defect-classes.md` (a new class is added there first). A correction to a row already in the tally
   goes in `tally-src/overrides.csv`, a missing report row in `tally-src/reports-extra.csv`; the grade-run group is
   regenerated with `python3 design/status/tally-src/g7/build.py` (its findings file adds a `caps` column). Then, from the repo root:
   `python3 design/status/tally-src/merge.py` (rewrites the three CSVs) and
   `python3 design/status/tally-src/metrics.py` (prints the new ranking). The raw group files are never edited.
3. **S6 measure:** `node tests/scripts/ws-status-index.mjs --conflicts --since <Wave 0 start commit or date>` on a
   full clone; target 0 conflicts on STATUS.md, index.html and `design/status/*`.
4. **E5 measure:** the same command over one week with six lanes running; met when no merge in that week
   conflicts on a shared file.
5. **WRM row at every deploy:** re-run `node tests/scripts/ws-wrm.cjs --report-only` and add a dated row below.
