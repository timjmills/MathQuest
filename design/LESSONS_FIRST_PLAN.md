# Lessons first — the K–5 short and long lessons at 8/10, unit by unit (plan v1, 2026-11-07)

Owner decision (2026-11-05 to 11-07, recorded in `design/STATUS.md:712`): "prioritize to make the shorter and longer
lessons of all our CCSS lessons first 8/10 and work on the skill families/skills related to those first." K–5, order (A)
"across all grades by time of year", method "using our automatic mechanical checks first, then testing, then adding our
findings to the next checks to get to 8/10 faster each time", "lets get as many agents/sessions going to get this done …
stop around 70%" of the weekly usage limit. Planned at high effort; **every agent and session that does the work runs on
Opus 5.5 at MEDIUM effort** (this replaces CLAUDE.md "Agents"' low-effort builder rule for this program only).

This plan is the work order for that decision. It does not change the bar: every lesson page, skill page and screen host
still passes only at ≥ 8 on every criterion of `design/audit/RUBRIC.md`, graded by an independent critic.

Files: this plan · the queue `design/lessons-first/QUEUE.md` + `design/lessons-first/queue.json` (generated by
`node tests/scripts/ws-lessons-first-queue.cjs`) · wave 1 briefs `design/lessons-first/briefs/*.md`.

## 0. In short (one screen)

- **What a unit is.** One White Rose block as one school grade teaches it (school rule: WRM Year N = grade N−1, so K = Y1
  … Grade 5 = Y6), plus the Awsaj CCSS BUILD lessons the school places in it. **80 units, 843 lessons in the school's K–5
  sequence, 817 CCSS lessons (64 of them CCSS BUILD), 26 non-CCSS lessons parked.** Each CCSS lesson needs a short lesson
  (the standard packet) and a long lesson (the detailed V22 pack): **1,628 products; 6 long lessons pass today.**
- **Order.** Round r = every grade's r-th unit by its first teaching week, K, 1, 2, 3, 4, 5 → **15 rounds**. Round 1 =
  K Place value within 10 · G1 Place value · G2 Place value · G3 Multiplication and division · G4 Multiplication and division
  A · G5 Place value: 85 CCSS lessons (11 BUILD), 59 skills (3 at 8/10), 32 build-list entries.
- **The real bottleneck is skills, not lessons.** Of the 343 skills the queue's lessons practise, **11 are at 8/10**
  (`js/modules/redesign-passed.js`); only **7 of 817** CCSS lessons have every skill passed. A lesson cannot pass before the
  skills it prints do (DETAILED_MAKER "Skill coverage rule"). So each unit is: its skills to 8/10 → its lesson cards → compile
  short + long → machine checks → critic → checks learned → deploy.
- **Prerequisites before unit 1 (critical path ≈ 6–8 working days):** lessons phase 0 fix round (branch
  `lessons-phase0`, critic r1 FAIL min 3) → the lesson compiler E4 (one card → short + long lesson; shapes; lesson
  precritic) → proof: recompile lessons 1–6 and pass, lesson 7 as a second hold-out. **In parallel from day 1:** the
  lesson-checks lane, and the pilot unit's skill lanes (operations + algebra for **G3-Y4.B4**, which already holds long
  lessons 3a, 4, 5 and 7). The pilot unit measures the real cost per unit before scaling.
- **Lanes:** 5 cloud sessions at once (one lane each, own container and browser slots) + the lead; in-session worktree
  agents only for the two in-flight items, auditors and one-off checks (≤ 2 at once: this container has 5.2 GB free and two
  browser slots). One merge train, twice a day, run by the lead.
- **Budget (newest figure: $20 ≈ 1 % of the weekly limit, `design/STATUS.md:701`).** At the 70 % cap ≈ $1,400 a week:
  lead ≈ 15 %, deploys and audits ≈ 5 %, **lanes ≈ 50 % ($1,000)**. Wave 1 (to the reset on Thu 11-12 22:00 UTC) ≈ **50–75 %**
  at full size including the lead, so it is launched in priority order and sized down to whatever this week has left. **Round 1 ≈ 200 % (≈ 4 weeks of lane budget).
  The whole queue at today's measured costs ≈ 1,800 % (±35 %) ≈ 36 weeks; at the loop's target (critic rounds 3+ → 1) about
  half.** That does not fit this school year without the loop working or a scope choice (owner question Q2).
- **Owner questions (§8):** Q1 WRM year → grade (suggest the school rule K = Y1 … G5 = Y6); Q2 scope (suggest: all CCSS
  lessons as you said, BUILD lessons first in every round, re-decide after the pilot's measured cost); Q3 start week; Q4 lesson

The queue counts lessons the way the school site counts them (one lesson = one line of the pacing: a small step or a BUILD
lesson). The short lesson is contained in the long one (DETAILED_MAKER: "P2 + P3 + P4 + Mixed the standard lesson packet fed
the description's `lessonData`"), so **one lesson card makes both** (§2.2): the long lesson adds the teacher pages and
P0 / P1 / P5 / P6.

### 1.2 The queue is generated, never hand-kept

`node tests/scripts/ws-lessons-first-queue.cjs` (pure node, ≈ 0.3 s, deterministic) writes:

lesson-engine lane adds the library's lesson grades (`ws-lesson-coverage` status db, phase 0) as a source when it lands, so
short-lesson passes are read from the record instead of the three sample constants the script holds today.

## 3. The per-unit pipeline (the recipe)

One unit goes through seven stages. A lane never starts a stage while the previous one's gates are red. "Clean before critic"
means `ws-precritic … --strict` plus the unit gates green **on the lane branch merged with the current integration branch**
(CLAUDE.md, LESSONS_LEARNED rule 0b).

| Stage | Who | What | Gates (exact) |
|---|---|---|---|
| 0 Pick | lead | regenerate the queue; brief the skill lanes with the unit's main skills not at 8/10 and its build entries (QUEUE.md, "Units in detail") | `node tests/scripts/ws-lessons-first-queue.cjs --check` |
| 1 Skills to 8/10 | the skill-family lane that owns each skill's generator (`build-list.js` `laneFor`) | per family: spec card drafted → **signed** → build (Opus medium) → precritic → independent critic (batch per family, RUBRIC + the visual-quality questions) → `redesign-passed.js` entry with evidence in the same change; build entries: new skill / option / preset with tags (SKILL_STANDARDS, SKILL_WRM, links `direct`/`pre`/`related`, search terms, appended share code) | `ws-spec-card --check-signed design/cards/<family>/<family>.md`; `ws-precritic --skill <every skill touched> --strict`; `ws-content-audit --skill`; `ws-visual-quality --skill`; `ws-standards`; `ws-search-terms`; `ws-code-snapshot`; `ws-presets-unit`; `ws-wrm --report-only`; `ws-wrm-page-unit`; `ws-lessonfit`; `ws-redesign-passed`; `ws-backtest`; `ws-boot-smoke` |
| 2 Lesson cards | the unit's lesson lane | `ws-lesson-card --draft --unit <id>` writes one card per CCSS lesson from data (step, CCSS / EE, main skills and option values per part from links + SKILL_WRM, prerequisite check from links `pre`, ranges and edge cases from the skill options, misconceptions from providers, vocabulary from `wrm-vocab.json`, shape from SHAPES.md); the builder writes only the story, the hook and the shape's teaching notes; every undecided line becomes a question with a suggested answer on the round's owner sheet | `ws-lesson-card --check-signed --unit <id>` |
| 3 Compile | lesson lane | `compileLesson(card)` → short (library entry) + long (detailed description) for every lesson of the unit | node: `ws-lesson-unit`, `ws-lesson-coverage`, `ws-lesson-card --check`; browser: `ws-lesson-check --unit <id>` (25 seeds, LESSON_RULES, LINK-1…5), `ws-detailed-lesson --lesson <id> --check --repeats` (each lesson), `ws-precritic --unit <id> --strict` (the §6.3 lesson checks + `--role lesson` + `ws-teacher-wrm`), `ws-lessons-first-queue --check` |
| 4 Critic | independent critic in the lesson lane's session (Opus medium) | the first two lessons of each **new shape**: every page graded in full (this certifies the shape); from a shape's third lesson: teacher pages in full, pupil pages batch-read + 1 in 5 in full (IMPROVEMENT_PLAN §1.6.3, §1.6.5 Lessons item 6); keys by machine + spot-check; short and long both | precritic table pasted; grades written to `design/lessons/grades.jsonl` (phase 0's record, read by `ws-lesson-coverage`) |
| 5 Findings → checks | lesson lane (checks in its own scope) or the checks lane (shared scripts) | every finding a machine could measure becomes a check with a backtest row (FAIL on the failed commit, PASS on the fix) on precritic's path, **before the next unit's critic**; the rest are tallied by class | `node tests/scripts/ws-backtest.mjs`; `node tests/scripts/ws-precritic-plan.mjs` (the new check is on the path) |
| 6 Deploy | lead | merge train (§4.4); deploy gates on the merged tree; owner go per round (one picture sheet per unit); stamp; push master | `bash tests/scripts/ws-deploy-gates.sh` (3 sessions); `node tests/scripts/ws-stamp-assets.cjs --check`; `ws-status-index --check` |
| 7 Speed reflection | an independent auditor (Opus medium, never the lane) | the unit's record `design/lessons-first/units/<unit-id>.md` (§6.2), plus `design/status/speed-audit.md` and `metrics.md`; regenerate the queue | `ws-lessons-first-queue --check` |

**A skill that only supports a lesson** (it appears only in the Prerequisite Check, P1 number sense or the Mixed page) does
not block the lesson's critic: its cells must pass the lesson's machine checks, and it is brought to 8/10 when its own unit
comes (prerequisites are mostly earlier skills, so by time order they usually pass first). Owner question Q8.

**A lesson whose links verdict is partial or gap** waits for its build entry; the unit is closed when every CCSS lesson
passes, but its other lessons deploy as they pass.

**Owner touchpoints, batched (Q4):** once per round, one sitting: (1) the round's skill-family spec cards and lesson cards —
only their undecided lines, each with a suggested answer, "all as suggested" accepted; (2) one picture sheet per unit
before it goes live (the go line). Nothing waits on the owner mid-round: a card question that arrives mid-round goes on the
lane's owner list (LESSONS_LEARNED rule 0).

## 9. Risks, and what the new priority throws off

- **The scale is honest but large.** 332 skills to bring to 8/10, 303 build entries and 1,628 lesson products. At today's
  costs it is about 36 weeks at 70 %; the school year has about 30 left (W09 of 38). If the loop does not cut critic rounds
  as targeted by round 3, the plan says so and asks Q2 again with the measured numbers.
- **The compiler is the single point of failure.** If E4's proof (lessons 1–6 recompiled) does not pass in two rounds at
  medium, rule 7 stops it: the lead writes the root-cause check and re-briefs. Until then lessons are not made by hand at
  scale (that path cost 3–4 rounds a lesson).
- **Skills first means lessons arrive late in each round.** The first lesson products of round 1 come in wave 2; most come in
  waves 3–5. Teachers see skills improve before they see lessons.
- **Engine edits void passed work.** Edits to `lesson-pages/*`, `roles/lesson.js` or `detailed-lesson.js` can change the six
  passed long lessons: P3 adds their `--check` to the deploy gates and every engine change re-renders them (`ws-lesson-hash`).
- **Shared-file collisions.** `links/<Y>.json`, `wrm.js`, `data.js` are touched by every skill lane; only the integrator
  merges them. A lane that hand-edits one is sent back.
- **Critic and owner capacity.** Five lanes produce up to five critic rounds a day and an owner sheet per round; batching
  (Q4) keeps the owner's time to one sitting per round.
- **Budget visibility.** In-session agents hide cost inside the lead's counter (the facts print and explorer rounds are not
  measurable today); §5.5 rule 3 fixes it for new work.
- **Machine limits.** 5.2 GB free here: more than two in-session worktrees will fill the disk; perf gates measured beside
  other browser work are void.
- **Thrown off or parked by this priority:** E1–E3 (every live skill makes every worksheet) for skills no lesson uses; the
  truly mixed Mixed-up layouts (PR #29); the answer-box option (PR #28); Highest number / decimals as an all-family lane
  (folded into family lanes); explorer nits; grade 6 and EE access lessons; the thinking pages (still paused); the 26
  non-CCSS White Rose lessons (parked at the end, kept per the owner's 2026-10-10 ruling); teacher-site work not needed by
  lessons. Each keeps its hand-over and resumes after the queue or when a unit needs it (§2.3).
- **The queue is only as true as the links files.** 125 of the 303 build entries exist only in the links files' own
  proposals, not on `build-list.js`; the first skill lane of each family merges the ones its unit needs into the build list
  (or the integrator does), so the queue and BUILD_LIST.md agree.
